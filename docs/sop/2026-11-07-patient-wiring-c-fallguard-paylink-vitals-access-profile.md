## Why
Backend #44 moved FallGuard scoring to the server, added the payment-link route and turned the missing-pricing 500 into a 503. Backend #43 made `PUT /auth/profile` save name and phone, validated vitals and fixed the vitals access grant, revoke and list (they used to compare a user id with a patient id). The app still sent a client score, had no way to re-pay after a restart, hid the sharing screen as "Coming soon" and carried a workaround that said "we couldn't save your name" after a 200.

## How
| Area | Decision |
|---|---|
| Spec | `OAKLY_BACKEND_DIR=<backend @ f3b0a7c> pnpm api:sync` (same generated files as branch `feature/apps-reset-by-code`; if both land, the second merge of these two files is a no-op). `FallGuardAnswerInput.score` is now optional and documented as ignored. |
| FallGuard | `toSubmitBody` sends `{ question_id, answer: option text }` only. The seeded question and option values are untouched. The option `score` from the question list is kept **only** for the "out of N" denominator on the result (never shown per option, never summed for the total: the total on screen is the server's). A refused submit is read by `detail.code` (`fallguardRefusal` in `src/domain/fallguard.ts`): `fallguard_unknown_question` and `fallguard_invalid_option` mean the questionnaire changed, so the answers are dropped, the question list is fetched again and the person starts at question 1 with a sentence saying so; `fallguard_no_answers` and `fallguard_duplicate_question` show a plain sentence. Everything else (500, offline) keeps the shared wording and the person on the last question. |
| Pay now | `usePaymentLinks` (in memory, as before) is used first. With no URL for the booking, "Pay now" calls `bookingService.paymentLink` through `fetchPaymentLink`, remembers the answer and opens it with the **same in-app browser flow** (`openCheckout` then the capped `verify-payment` poll). `409 booking_already_paid` is good news: the bookings are refreshed and the normal payment check confirms it. `409 booking_already_cancelled / booking_not_payable / payment_window_expired / payment_under_review`, `403 not_your_booking` and `404 booking_not_found` end the flow: the screen says why, drops "Pay now" and offers View booking. `409 payment_link_in_progress` is asked again once a second (3 tries) and never shown as an error. Any other refusal (**503 `payment_link_unavailable`**, **503 `payment_check_unavailable`**, offline) keeps "Pay now" and also offers "Cancel this booking" (free). Sentences live in `PAYMENT_LINK_MESSAGES` (`src/api/bookingErrors.ts`). |
| Pricing 503 | `503 booking_settings_not_configured` (a database with no pricing row) on preview or create now reads "Booking isn't available right now. Please try again later." through `bookingErrorMessage` (the booking summary and its quote error used the generic mapper before, which already showed the server's own sentence). |
| Vitals sharing | `GET /vitals/access/list` (active grants, with `caregiver_name`), `POST /vitals/access/grant`, `POST /vitals/access/revoke`, all with the **profile ids** (`patient_id` from `/auth/me` -> `patient.id`, `caregiver_id` from a booking's `caregiver_id`). There is no caregiver search, so the people one can share with are the caregivers on the patient's own bookings (cancelled and declined ones left out, one row per caregiver, already-shared ones moved up). Health data: every grant opens a confirm dialog naming the caregiver ("will be able to see and add to your vitals until you stop sharing"); stopping is confirmed too and afterwards the screen says it took effect at once **but a caregiver in the middle of a visit keeps access until it ends** (guide section 5.1). Refusals are plain strings on these routes, so the exact sentences are matched in `src/domain/vitalAccess.ts`. |
| Profile | `useUpdateProfile` sends only the non-blank values the person touched, then `/auth/me` is re-read; a 200 now means saved, and the boxes show what the server kept (a phone comes back without spaces: `+234 000 071 8205` becomes `+2340000718205`). The refusal is the server's own sentence: `422` list -> `detail[0].msg` under the field named by `loc` (`full_name`, `phone_number`); `409 phone_number_taken` under the phone; any other coded refusal (`email_change_not_supported`, `photo_upload_only`, `use_change_password`) in a dialog. The email stays read-only with "To change your email, contact support." An emptied phone box is refused on the screen ("Enter a phone number, or leave it as it is."): the server removes a phone only for an explicit `null`, and there is no "Remove phone number" action in v1. |

## Verification
- Tests added or rewritten: FallGuard (no `score` on the wire, the four 422 codes by capture, reload and restart at question 1, plain sentence for a 500); Pay now (link requested with no body and opened in the browser, reused on the next tap, already paid confirms, cancelled and expired close the flow, 503 `payment_link_unavailable` and `payment_check_unavailable` keep Pay now and offer cancel, `payment_link_in_progress` waited out, someone else's booking, pricing 503); vitals sharing (list, confirm then grant with the captured request body, stop sharing and the visit-in-progress note, cancel sends nothing, 404 sentences, filters, retry); profile (real save with the captured request and the separator-free phone, 422 bad phone, 409 taken, 400 dialog, blank-phone refusal).
- Local CI: frozen install, api types drift check, typecheck, lint, tests single-worker (`jest -i`) and the admin build: see the report for the final run. The process exits on its own (no `--forceExit`).
- **Not verified:** a real device, the real Paystack checkout, any real push; the **real Paystack answer to a repeated payment reference** (the backend itself marks this "expected to fail": its captures used a fake Paystack, so against the real one every `payment-link` call for a booking that `/create` already started may be `503 payment_link_unavailable`); the AI summary text; `payment_link_in_progress`, `payment_under_review` and `booking_not_payable` (backend tests only, so their bodies in the app tests are typed from the guide's table, not captured); `phone_number_required`, `photo_upload_only` and `use_change_password` (typed from the guide).

## Operate / roll back
Revert the branch. No backend change is needed and none was made. The app works against `main` at `f3b0a7c` or later; against an older backend the new routes would answer 404.
